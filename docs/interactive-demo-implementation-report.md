# VisePanda Early Access Demo 实现汇报

> 版本：2026 年 8 月 25 日  
> 对应仓库：`JTCAO515/VP-Early-Access`  
> 文档用途：说明当前 Demo 已经实现的页面结构、功能、数据模型和交互状态，供正式产品开发参考。  
> 事实边界：本文描述的是可交互静态 Demo，不代表真实 AI、用户账号、库存、预订、支付、叫车或人工服务已经接入。

## 一、Demo 现在是什么

当前 Demo 不是一组产品截图，而是一套可以点击的网页版产品模型。它把 VisePanda 的主要能力放进同一个浏览器框架中，让访客看到一条完整路径：

```text
提出旅行需求
  → 补充缺少的信息
  → 生成 Trip Canvas
  → 查看来源、风险和待确认项
  → 用户确认改动
  → 在 Today、Tools、Explore 和 Copilot 中继续执行
```

Demo 的核心不是“AI 给出一份行程”，而是下面四件事：

1. Chatbot 和 Trip Canvas 共用一份行程状态；
2. 任何行程修改都先进入 Diff，由用户确认；
3. 价格、规则、开放时间等信息带来源、置信度和复核时间；
4. 行程出问题时，系统给出下一步和恢复方案，而不是重新生成一份互不相干的计划。

## 四、Demo 浏览器框架

### 4.1 桌面端结构

桌面端使用接近 16:9 的浏览器窗口。框架分为四层：

```text
浏览器标题栏
├─ 地址：www.go2china.space/visepanda
├─ Demo fixture 标识
└─ 全屏按钮

应用主体
├─ 左侧导航
│  ├─ Today
│  ├─ Ask VisePanda
│  ├─ Copilot
│  ├─ Tools
│  ├─ Explore
│  ├─ 11 段聊天历史
│  └─ User
└─ 右侧工作区

底部状态栏
├─ 当前 Trip
├─ 当前城市或行程上下文
├─ Demo 固定时间
├─ 四种状态说明
└─ 四步产品引导
```

左侧聊天记录是唯一独立滚动的侧栏区域。User 固定在底部，不会被聊天列表挤出去。

### 4.2 全屏模式

导航、Hero 按钮和六张能力卡都可以直接打开全屏 Demo。

- Demo 占满浏览器视口；
- 页面背景停止滚动；
- 点击退出按钮或按 `Esc` 返回；
- 原来的 Demo 位置保留高度，退出后页面不会跳动；
- 外部入口可以直接指定打开 Ask、Today、Copilot、Tools 或 Explore。

### 4.3 移动端结构

375×812 和 430×932 使用移动布局：

- 顶部保留浏览器地址和 Demo 状态；
- 聊天历史改成横向滚动；
- 顶层功能改成底部六项导航；
- Ask 页面增加 `Ask / Trip Canvas` 分段切换，不再左右并排；
- Diff、POI 详情和菜品详情改成底部抽屉；
- 交通、酒店等对比表改成纵向卡片，避免页面横向滚动。

### 4.4 独立分享页 `/demo`

`https://earlyaccess.go2china.space/demo` 是 Demo 的独立沉浸式入口。

- 直接访问或刷新 `/demo` 都会进入完整产品框架；
- 页面始终保持全屏，不依赖主页的全屏状态；
- 浏览器栏提供中英文切换；
- “返回主页”回到 Early Access 页；
- 主页 nav 和 Hero 的“打开 Demo”都指向这个地址；
- 六张能力卡继续使用主页内的定向深链；
- 独立页和主页内嵌 Demo 共用同一个 `ProductDemo` 和同一份 `lib/demo/` fixture。

## 五、全局状态、来源与置信度

Demo 使用四种统一状态：

| 状态 | 含义 | 常见位置 |
| --- | --- | --- |
| Confirmed / 已确认 | 用户已经确认 | Canvas 节点、记忆、POI |
| Proposed / 待确认 | 等待用户决定 | Canvas Diff、预订动作 |
| Inferred / 推断 | 系统根据行为或对话推断 | 用户画像、备选节点 |
| Recheck / 需复核 | 信息可能已经过期 | 票价、签证、开放时间、支付支持 |

置信度分为：

- High confidence / 置信度高；
- Medium confidence / 置信度中；
- Needs recheck / 需复核。

来源分为：

- Official / 官方渠道；
- Platform / 公开平台；
- Your upload / 用户上传。

每个 Evidence Chip 至少显示来源名称和复核时间，可选显示有效期。价格、时间、规则、支付和签证结论不应该脱离 Evidence 单独出现。

## 六、Today

Today 回答两个问题：现在应该做什么，计划有变时怎么办。

### 6.1 下一步

下一步卡片显示：

- 节点名称；
- 建议出发时间；
- 交通方式与预计耗时；
- 随身要带的东西。

当前示例是从酒店前往武康路，并提示护照、中英文地址卡和过敏说明卡。

### 6.2 当前条件

展示固定 Demo 条件：

- 天气；
- 空气质量；
- 预警；
- 今日闭馆信息。

这些值是固定 fixture，不读取实时环境数据。

### 6.3 四条恢复路径

| 情况 | Demo 中的处理 |
| --- | --- |
| 交通延误 | 取消无法赶上的节点，保留还能调整的晚餐 |
| 地点闭馆 | 换成无需门票的滨江节点 |
| 排队过长 | 换到附近的第二家备选餐厅 |
| 身体不适 | 下午只保留一个室内节点，并给出医疗渠道 |

恢复方案不会直接改 Canvas。点击后只能生成待确认 Diff。

### 6.4 九项行程检查

| 检查项 | 当前状态类型 |
| --- | --- |
| 路线可行性 | Pass |
| 转场时间 | Watch |
| 首末班 | Not workable |
| 开放时间与闭馆日 | Watch |
| 预约状态 | Not workable |
| 排队与人流 | Watch |
| 天气敏感度 | Pass |
| 预算 | Watch |
| 硬约束 | Pass |

不可行项会显示原因、Evidence 和两个备选方案。用户可以把备选方案送进 Diff。

## 八、Trip Canvas

### 8.1 Canvas 文档结构

每份 Canvas 包含：

```ts
CanvasDoc
├─ title / subtitle
├─ days[]
│  ├─ day summary
│  ├─ stay
│  └─ nodes[]
├─ compare table（可选）
├─ versions[]
├─ diff（可选）
└─ bookings[]
```

### 8.2 节点字段

| 字段 | 说明 |
| --- | --- |
| `id` | 节点唯一标识 |
| `time` | 时间或相对时间 |
| `title` | 中英文标题 |
| `kind` | sight、food、transit、stay、task |
| `duration` | 停留时间 |
| `transfer` | 与上一节点之间的交通 |
| `cost` | 固定示例费用或区间 |
| `state` | confirmed、proposed、inferred、recheck |
| `confidence` | high、medium、recheck |
| `evidence` | 来源、复核时间、有效期 |
| `risks` | 排队、闭馆、天气、过敏等 |
| `next` | 静态外部渠道动作 |
| `map` | Demo 示意图上的相对坐标 |

### 8.3 三个视图

Timeline：

- 按天显示；
- 顶部显示步行距离、主要节点、预算和室内比例；
- 展开节点后显示风险和 Evidence；
- Day 之间显示住宿地和次日出发时间。

Map：

- 使用节点的 0 到 1 相对坐标；
- 连接同一份 Canvas 中的节点；
- 显示节点序号、名称和状态；
- 是动线示意图，不是真实地图。

Bookings：

- 汇总需要购票、预约、查看酒店或打开官方渠道的节点；
- 每项显示状态和操作按钮；
- 按钮只给出静态反馈，不产生订单。

### 8.4 版本

支持多份预置 Canvas 版本，例如：

- 初版；
- 加入夜景；
- 减少步行后的当前版。

切换版本会显示版本说明，但不会读取历史数据库。

### 8.5 Diff 与确认

当前共有 12 条预置 Diff，分布在上海、攻略导入、家庭同行、延误恢复和预算下调等场景。

Diff 支持：

- add、remove、move 三种操作；
- 显示修改对象、细节、原因和触发来源；
- 逐条接受；
- 逐条拒绝；
- 换一个方案；
- 全部接受。

接受或拒绝只改变当前浏览器中的组件状态。页面刷新后会回到 fixture 初始状态。

## 九、攻略导入检查

导入面板包含四个阶段：

1. 已接收；
2. 解析中；
3. 已抽取；
4. 已检查。

当前固定示例包含 5 个抽取字段：日期、城市、POI、高铁字段和酒店区域。

- 每个字段显示置信度；
- 普通字段可以在两个预置值之间修改；
- 无法识别的高铁字段显示失败状态；
- 点击手工补充后改为 `G192`；
- 检查完成后可以打开 Canvas Diff；
- Demo 不上传、识别或保存真实文件。

## 十、菜品抽屉与点菜卡

餐厅 Canvas 可以打开菜品抽屉。当前展示三道菜：

- 红烧肉；
- 葱油拌面；
- 含花生酱汁的白斩鸡。

每道菜显示口味、原料、过敏原、搭配和价格。

花生是 Michael Turner 画像中的硬约束。命中花生的菜会进入警告状态，并提供替换建议。

抽屉底部有一张中文点菜卡：

```text
我对花生过敏，请不要加花生或花生油。
```

这张卡是固定示例。用户仍需与餐厅确认。

## 十一、Copilot 长期记忆

Copilot 只负责长期记忆，不再承载 Tools。

| 维度 | 示例 |
| --- | --- |
| 旅行强度 | 舒适，每天约两个主要节点 |

### 11.2 每条记忆的字段

- 维度；
- 当前值；

- 状态；
- 置信度；
- 来源；
- 更新时间；
- 已经影响过哪些行程建议。

- 确认记忆；

- 暂停或恢复长期记忆；
- 导出固定 JSON 预览；
- 查看 Before/After；
- 跳回 Canvas 查看改动。

硬约束不能被自动覆盖。

- 已联网；

离线时，双语地址和已保存卡片仍然可见，需要联网的查询与渠道操作会被禁用。

## 二十一、按 Demo 优化正式开发的建议顺序

### P0：Chatbot 与 Trip Canvas

先完成最小闭环：

```text
用户消息
  → 结构化 Travel Intent
  → Canvas Proposal
  → schema / safety 校验
  → 用户确认
  → applyPatch(expectedVersion)
  → 新 Canvas 版本
```

这一步需要：

- 一个 Canvas 写入者；
- 乐观锁或版本号；
- append-only 事件或可恢复快照；
- Proposal 与应用后的状态分离；
- 拒绝和换方案反馈进入审计记录。

### P1：长期记忆

- 区分用户直接设置、用户确认和系统推断；
- 每条记忆保留来源和更新时间；
- 硬约束单独建模；
- 支持确认、修改、忘记、暂停、导出和删除；
- Ask 引用记忆时可以回看来源。

### P2：Evidence 与 Live Fact

- Fact 与来源分离；
- 记录 provider、retrievedAt、TTL 和有效期；
- 过期后进入 Recheck；
- provider 失败时显示 stale/unavailable，不用旧值冒充最新；
- 用户上传只作为证据，不直接成为已审核事实。

### P3：Tools

按独立工具接入，不把工具逻辑写进 Chat 组件：

- 翻译；
- 叫车；
- 签证与法规；
- 网络与电话卡；
- 人工介入。

每个工具需要独立 provider adapter、能力边界、失败状态和 Canvas Proposal 输出。

### P4：Explore

- 先冻结 Canonical POI 和 PoiFactSchema；
- POI 进入 Canvas 时只写精确 POI ID 和 Trip Place Reference；
- 支付、语言、预约等字段逐项存储；
- 对来源、复核和过期做字段级处理；
- 不把外部平台内容直接批量复制进内部知识库。

### P5：Today 与恢复路径

- 根据当前 Canvas、时间和外部条件计算下一步；
- 延误或闭馆触发恢复 Proposal；
- 方案应用仍走 Canvas Diff；
- 紧急渠道排在普通产品帮助之前；
- 支持离线查看已保存地址、计划和过敏说明。

### P6：User、Auth 与数据治理

- 接入真实 Auth 后再建立 User ID；
- 明确账户资料、旅行画像和长期记忆的所有权；
- 为导出、删除和暂停记忆建立真实后端流程；
- 不把 Demo 的删除确认态当成已经删除数据。

## 二十二、正式开发验收清单

### Chat 与 Canvas

- [ ] Chat 和 Canvas 使用同一个 Trip ID；
- [ ] 所有模型修改先成为 Proposal；
- [ ] Proposal 未确认前 Canvas 不变；
- [ ] 并发写入返回可恢复冲突；
- [ ] 版本回滚不丢失审计记录。

### Memory

- [ ] 每条记忆有来源、状态和更新时间；
- [ ] 推断可以被用户否定；
- [ ] 硬约束不能被普通偏好覆盖；
- [ ] 暂停记忆后 Ask 不再引用；
- [ ] 删除和导出有真实后端证据。

### Evidence

- [ ] 价格、时间、规则和支付结论都有来源；
- [ ] TTL 到期进入 Recheck；
- [ ] provider 失败有明确降级；
- [ ] 页面不把缓存值写成实时值。

### Tools

- [ ] 每个工具有独立能力边界；
- [ ] 真实外部动作前再次确认；
- [ ] 失败不会静默写入 Canvas；
- [ ] 写回行程时生成 Proposal；
- [ ] 叫车、支付、预订和人工联系有审计记录。

### Explore

- [ ] POI ID 稳定；
- [ ] 支付/语言/预约字段带 provenance；
- [ ] 加入 Canvas 后保留原 POI 引用；
- [ ] 不把未知字段写成默认支持；
- [ ] 筛选条件在移动端同样可用。

### UX

- [ ] 1440×900、375×812、430×932 无横向溢出；
- [ ] 中英文切换后不截断；
- [ ] 键盘可以走完主要功能；
- [ ] Reduced Motion 下不自动播放；
- [ ] 全屏进入和退出后页面位置不跳；
- [ ] 错误和降级状态可被用户看见。

## 二十三、结论

这套 Demo 已经把 VisePanda 的产品骨架表达清楚：Chatbot 负责把问题问清楚，Trip Canvas 保存唯一行程状态，Copilot 管长期记忆，Tools 处理旅途中的具体事务，Explore 管地点，Today 负责下一步和应变。

正式开发时，最值得保留的是信息架构、类型和“先提案、再确认”的写入规则。固定数据、假用户和只在浏览器里切换的状态只能继续留在 Demo 中。
