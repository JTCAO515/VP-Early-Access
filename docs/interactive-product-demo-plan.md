## 0. 本轮扩写范围

本轮只扩写「展示什么、展示成什么样」，不改变已冻结的页面结构、CTA 落点和数据边界：

- 补全每个界面的字段级规格，使 Demo 能被逐屏实现和逐屏验收；
- 补全证据、来源、复核时间、置信度和不确定回退的可视化规则；
- 补全空态、加载、失败与降级状态，让 Demo 看起来像真产品而不是静态图；
- 补全 Canvas Diff、版本回滚、Today 与恢复路径这条真正体现产品能力的主线；
- 把交互状态矩阵、实施切片和验收标准同步到新的规模。

反目标：不新增真实交易、不新增真实 provider 调用、不新增注册人数或媒体背书、不修改 Early Access 表单落点。

## 1. Demo 核心目标

用户应在 1–2 分钟内理解：

1. Chatbot 如何通过追问理解旅行需求；
2. Trip Canvas 如何承接并组织旅行结果；
3. Copilot 如何通过长期对话形成用户记忆和旅行画像；
4. Explore 如何完成城市、POI 与执行工具的发现；
5. VisePanda 如何把行程检查、确认、下一步和恢复路径组织在一个产品内；
6. VisePanda 在哪些地方明确承认自己不确定，并给出官方渠道与恢复路径。

产品宣传顺序：

```text
Chatbot / Trip Canvas
  -> 用户长期记忆与画像
  -> Explore / 多执行工具
  -> 行程模拟器：导入、检查、确认
```

### 1.1 一分钟主线脚本（已实现）

Demo 默认落在「上海三日游」，并在右下角提供一个 `跟着走一遍 / Take the tour` 的静态引导条，四步：

| 步 | 落点 | 用户看到的能力 |
| --- | --- | --- |
| 1 | Ask → 上海三日游 | 追问、澄清、生成 Canvas |
| 2 | Canvas → Diff | 变化先提案、用户确认后才应用 |
| 3 | Copilot | 长期记忆如何改写下一次建议 |
| 4 | Ask → 攻略验证 | 导入既有计划、发现不可行节点、给出替代 |

引导条只切换已预置状态，不播放动画视频，不自动前进。

### 1.2 每个界面必须回答的问题（已实现）

每个主界面在标题区固定展示一句能力陈述，避免用户只看到 UI 却看不懂价值：

- Ask：`把模糊的想法问清楚，再落成行程。`

## 4. Ask VisePanda / Trip Canvas

Ask 页面统一采用：

- 左侧：Trip Canvas；
- 右侧：Chatbot；
- 对话和 Canvas 内容同步切换；
- Canvas 变化先展示，再由用户确认；
- 预订、叫车、购买按钮只展示跳转能力，不开启真实交易。

### 4.0 对话通用交互层（已实现）

所有聊天共用同一套消息构件，避免每个场景各写一套：

- **澄清问题 chip**：助手一次最多给出 3 个可点选项 + 1 个自由输入位；点选后追加为一条用户消息并切换到下一个预置状态。
- **生成中状态**：`正在生成 Trip Canvas` 带进度骨架，骨架结构与最终 Canvas 一致，不使用旋转菊花。
- **证据 chip**：助手消息底部可挂 0–3 个来源 chip，展示来源名、类型（官方 / 平台 / 用户上传）、复核时间。
- **置信度**：涉及时刻表、开放时间、签证与支付的结论必须带 `高 / 中 / 需复核` 三档标记。
- **不确定回退**：当结论不能确认时，助手不猜测，改为输出「无法确认 + 官方渠道 + 用户可执行的下一步」三段式。
- **消息操作**：复制、加入 Canvas、要求换一个方案、指出这条不对；后两个切换到预置的修正状态。
- **引用回看**：助手引用长期记忆时，展示 `来自你的画像：每日预算 USD 180–260`，点击跳转 Copilot 对应条目。

| 字段 | 说明 |

| 费用 | 预估区间，标记 Demo fixture |
| 状态 | 已确认 / 待确认 / 推断 / 需复核 |
| 证据 | 来源 + 复核时间 + 有效期 |
| 风险 | 排队、闭馆日、天气敏感、末班车 |
| 下一步 | 预订、购票、导航、翻译，均为静态跳转 |

三个视图：

- **Timeline**：按日按时间排列，展示节点全字段；
- **Map**：展示当日节点序列与移动线，节点与 Timeline 双向高亮；
- **Bookings**：把所有需要外部动作的节点聚合成清单，展示状态与官方渠道入口。

### 4.8 Canvas Diff 与确认（已实现）

这是 Demo 最核心的一屏，必须做实：

- 变化以 Proposal 形式出现，Canvas 顶部出现 `3 处改动待确认` 条；
- Diff 用三色标记：新增、删除、移动；
- 每条改动展示「为什么」：触发原因（用户消息 / 画像 / 检查结果 / 外部条件）；
- 操作：全部接受、逐条接受、逐条拒绝、要求换方案；
- 接受后 Canvas 才更新，并在节点上留下 `已确认` 徽标与时间；
- 拒绝后记录为一次负反馈，并在 Copilot 出现对应条目。

### 4.9 版本与回滚（已实现）

- Canvas 顶部提供版本下拉，展示 3 个预置版本：初版、加入夜景后、减少步行后；
- 切换版本时展示与当前版本的差异摘要；
- 提供「回到这个版本」按钮，切换到对应预置状态。

### 4.10 Today 与恢复路径（已实现）

`Today` 展示「此刻」的三块内容：

1. **下一步**：下一个节点、出发时间、交通方式、需要携带的东西；
2. **当前条件**：天气、空气质量、预警、闭馆提醒，全部标记为 Demo fixture；
3. **恢复路径**：当出现延误、闭馆、排队过长、身体不适四种情况时，各给一条预置的替代方案，并说明会如何改写 Canvas。

恢复路径的每个方案都走 §4.8 的 Diff 流程，不直接改行程。

- 中文用简体，避免直译腔；英文避免营销夸张词；
- 状态词全站统一：已确认 / Confirmed、待确认 / Proposed、推断 / Inferred、需复核 / Recheck；
- 中文长句在窄容器换行后不得截断，英文长词需允许断词；
- 不在文案中出现「实时」「保证」「最优」「唯一」等无法兑现的措辞。

## 18. 竞品能力对照（已实现）

能力区块之后、交互 Demo 之前展示四类产品的品类级定位对照：

- 传统 OTA：库存、实时价格和交易闭环最强；跨工具执行与长期旅行画像不是主要优势；
- 通用 AI：开放对话和广泛知识最强；旅行状态、来源复核与交易执行不稳定；
- 旅游 AI：目的地发现与行程生成更专业；中国本地支付、语言、规则和恢复路径深度因产品而异；
- VisePanda：突出 Chatbot × Trip Canvas、长期画像、来源/复核、多执行工具与恢复路径。

VisePanda 必须同时公开当前不足：酒店和票务库存、实时价格、即时交易暂时弱于传统 OTA。页面只声明「官方渠道跳转、后续渠道接入与合作扩展能力」，不声明已经与任何 OTA、酒店、票务或叫车平台建立合作。

对照是品类层面的产品定位，不点名具体竞争品牌，不写未经来源支持的市场份额、转化率或优胜排名。
